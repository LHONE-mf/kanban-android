# P19.6 и P19.8 · Переход на SQLite

Рабочая сборка использует IndexedDB. Проверочный перенос создаёт отдельный снимок из живой IndexedDB на Android или из копии ZIP v1 на Linux. Схема использует SQLite из Android без новых зависимостей. Полная приёмка обновления и прерываний через WebView потребуется до переключения хранилища.

## Схема и границы записи

- Таблицы досок, колонок и задач сохраняют исходные ID, порядок и даты. Составной внешний ключ привязывает задачу к колонке в её доске. Отложенный внешний ключ привязывает подзадачу к родителю в этой же колонке. Проверка снимка дополнительно исключает циклы.
- Чек-лист и результаты используют свои идентификаторы в пределах задачи. Ссылка вложения на результат включает ID задачи. Два вложения могут ссылаться на одни байты и при этом сохранить разные ID и имена.
- Имя файла строится из проверенного SHA‑256. Приложение будет принимать идентификатор вложения и получать путь по запросу SQLite. Имена из импорта никогда не определяют путь для записи. Подготовленный файл синхронизируется и переименовывается в пределах приватного тома до транзакции, которая публикует ссылку на него. Временный файл и неподтверждённая ссылка удаляются по одному и тому же идентификатору операции.
- Удаление задачи убирает её связь с медиа. Физическое удаление выполняется после договорённого окна отмены и проверки ссылок во всех задачах, результатах и незавершённых операциях. Сборщик сирот и публикация вложений должны выполняться последовательно. Отменённая операция не удаляет байты, используемые другой задачей.
- Настройки, план дня, напоминания, Pomodoro и японский прогресс входят в снимок. Для Android-уведомлений потребуется перестроение расписания по данным активной БД. Состояния планировщика и доставленных напоминаний обновляются после переключения.

## Проверка снимка на Linux

```sh
python3 tools/verify_p19_storage.py /path/to/comrade-backup.zip /path/to/new-snapshot
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'test_p19_storage_schema.py' -v
```

Подготовка сохраняет ФС и SQLite в соседней папке `new-snapshot.staging`. Перед публикацией инструмент проверяет SHA‑256 всех записей, сравнивает данные досок и задач, выполняет `foreign_key_check` и `integrity_check`. Завершённая папка публикуется одним переименованием. Повторный запуск с тем же архивом использует уже проверенные байты. Повторный запуск с другим архивом требует другой папки. Инструмент открывает исходный ZIP только для чтения.

На синтетической копии проверены остановка после публикации временного медиафайла, повторный запуск, общие байты с разными ID, принадлежность результата задаче и архивы с неверным хэшем или путём.

## Переключение в приложении

1. Снять согласованный снимок IndexedDB и сохранять пакетные позиции переноса в приватной SQLite. Для контроля повторов использовать постоянные ID, исходные размеры и хэши. В процессе подготовки исходный WebView продолжает пользоваться IndexedDB.
2. При финальной сверке дождаться текущих сохранений, временно заблокировать новые записи, повторно сверить каждую доску, связь, настройку и файл. При отличиях обновить снимок и повторить проверку.
3. Переключить источник загрузки одним изменением метаданных после успешной сверки. На следующем запуске сначала читать эти метаданные. Снимок старой IndexedDB сохранить до отдельного решения об очистке. После первого нативного сохранения восстановление возможно из проверенной копии актуальной SQLite и её файлов.
4. Проверить обновление поверх текущей APK. Повторить с принудительной остановкой после записи каждого файла, после синхронизации файла, после коммита БД, до и после переключения, во время удаления и отмены. До открытия нативного пути для записи сверить реальный снимок с исходным приложением.

Точка продолжения P19.6/P19.8 — пакетные операции рабочих данных, затем испытания переключения. Пробный снимок проверяет схему и порядок публикации файлов на Linux и Android.

## Проверочная копия на Android

В меню Comrade на Android доступно действие «Проверить перенос в SQLite». IndexedDB отдаёт задачи, настройки и ссылки на Blob в одной транзакции чтения. Вложения передаются по частям через существующий ZIP-мост. Android сверяет SHA‑256, сохраняет бинарные файлы по их хэшу и проверяет содержимое SQLite и её внешние ключи перед атомарной публикацией.

Копия находится в приватном каталоге `no_backup/sqlite-snapshot`. При повторе уже сверенные байты используются повторно. После успешной публикации из каталога снимка удаляются файлы, на которые ни одна запись нового снимка не ссылается. При сбое ранее опубликованная копия остаётся доступной. Рабочая база остаётся в IndexedDB. Для переключения ещё требуются пакетное чтение и запись из готового снимка и приёмка обновления на Android.
